03: Interactions

Choosing the Right Trigger

Not every interaction is a tap. Picking the correct trigger makes your prototype feel native — and catches usability issues that "On Click only" prototypes miss.

👆

On Click

Standard tap/click. The default for almost all navigation.

🖱️

On Hover

Reveals tooltips, dropdowns, or sub-menus on desktop.

✌️

On Drag

Swipe-to-navigate carousels, drawers, and card stacks.

⏱️

After Delay

Auto-advances — splash screens, loading states, onboarding.

⌨️

Key / Gamepad

Keyboard shortcuts for desktop apps and accessibility testing.

Teaching Tip: Ask: "How does Instagram's story tap-advance work in Figma?" (After Delay + Navigate). "How does a bottom sheet swipe up?" (On Drag + Move In). Getting students to map real app interactions to Figma triggers builds mental models for both tools at once.
04: Smart Animate

Smart Animate — Figma's Secret Weapon

Smart Animate automatically interpolates between matching layers across two frames, producing fluid transitions that look like real app animations — with zero code.

✅

When it works

  • Layer names match exactly across both frames
  • Elements change position, size, or opacity
  • Used with Components and Auto Layout
❌

When it breaks

  • Layer names differ between frames
  • Layers are in different groups/frames
  • Too many mismatched layers (becomes chaotic)

💡 The naming rule: If a button called "CTA Button" moves from bottom to top between two frames, Figma will animate it flying up — automatically. Rename it to "Button" on one frame and the magic breaks. Layer naming IS the prototype logic.

Teaching Tip: Live demo — duplicate a frame, move a card element to a different position, set Smart Animate, hit play. The gasps when it animates smoothly are reliable every time. Then break it on purpose by renaming a layer — showing exactly why naming discipline matters.

🖼️ Frames as Screens

One frame = one screen state in your prototype.

How to think about it

Every screen in your app — the home screen, a modal, an error state, a success confirmation — gets its own Frame in Figma. Prototype connections always start from an element inside a frame and point to another frame as the destination.

Practical rule

If a user action changes what they see significantly — it needs a new frame. A tooltip appearing? Use an interactive component instead. A new page loading? New frame.

📐 Set your device frame: In the right panel, under Frame, choose a device preset (iPhone 15, Pixel 8, etc.) so your prototype plays at the correct size in the preview player.

🎯 Hotspots

The interactive zone — any element can be one.

Creating a hotspot

1
Select any element (button, image, text, icon) inside a frame.
2
Switch to the Prototype tab in the right panel (or press Shift+E).
3
Hover over the element — a blue ⊕ handle appears on the right edge. Drag it to the destination frame.

⚠️ Tip: You can draw a hotspot over an empty area too — useful for testing if users discover hidden tappable zones (and they often won't, which is a usability finding).

👆 Triggers

What the user does to fire the interaction.

  • On Click — tap or mouse click. Use for almost all navigation.
  • On Hover — cursor enters the element's bounds. Desktop only — menus, tooltips.
  • On Drag — click and drag. Carousels, bottom sheets, swipe-to-delete.
  • After Delay — triggers automatically after N milliseconds. Splash screens, loading states, auto-advancing onboarding.
  • Mouse Enter / Leave — more precise hover control for desktop UIs.
  • Key / Gamepad — keyboard shortcut triggers. Useful for desktop app or kiosk prototyping.

✨ Transitions & Animations

Choose the transition that matches the navigation intent.

  • Instant — cut. No transition. Use for testing flow logic before investing in animation.
  • Dissolve — crossfade. Modal overlays, overlay states, gentle screen changes.
  • Smart Animate — matches and interpolates layers by name. Best for hero transitions, expanding cards, tab switches.
  • Move In / Move Out — slide directionally. Simulates push navigation (next page) or back navigation.
  • Push — both screens move together, one pushing the other off. Standard mobile page push.
  • Slide In / Slide Out — new screen slides over the current one. Bottom sheets, drawers, modals.

💡 Animation direction tells a story. Moving right = going forward. Moving left = going back. Moving up = drawer or bottom sheet. Users read direction as hierarchy.

📜 Scrolling & Overflow

Make your prototype scroll like the real app.

Enabling scroll

1
Select the Frame. In the right panel, find Prototype → Overflow.
2
Set to Vertical Scrolling (or Horizontal for carousels).
3
Make the content inside the frame taller than the frame itself — the overflow becomes scrollable in preview.

Fixed elements (sticky nav / tab bar)

Select an element (e.g. a nav bar), then in the right panel enable Fix position when scrolling. It stays put while the rest of the frame scrolls beneath it.

🧩 Interactive Components

State changes without navigating to a new frame.

What they solve

A toggle switching on/off, a checkbox being checked, a button hovering — these are state changes, not page navigations. Without interactive components, you'd need a separate frame for every possible UI state. With them, you keep the logic inside the component.

How to build one

1
Create a component and add Variants — one per state (Default, Hover, Active, Disabled).
2
In the Prototype panel, draw connections between variants (e.g. Default → Hover on Mouse Enter).
3
When an instance of this component is used in any frame, it carries those interactions automatically.

👆 On Click

When to use it

The default for nearly all app navigation — buttons, list items, cards, icons. On mobile this corresponds to a tap. On desktop, a single left-click.

💡 Test assumption: If users don't click your element during testing, it's either not discoverable or doesn't look interactive. That's usability data.

🖱️ On Hover

When to use it

Desktop-only interactions: dropdown menus appearing on hover, tooltips, image overlays, and revealing secondary actions. Never rely on hover for mobile prototypes — there's no hover state on touch screens.

⚠️ Do not test hover-dependent interactions on a phone. The flows will be completely broken for mobile users.

✌️ On Drag

Best for

  • Carousel / image gallery swipe
  • Bottom sheet drag-up to expand
  • Card stack swipe (Tinder-style)
  • Side drawer / hamburger menu slide-in

How to set it

Select trigger → On Drag. Choose direction (Left, Right, Up, Down). Pair with a Move In / Slide animation in the matching direction for maximum realism.

⏱️ After Delay

Best for

  • Splash / launch screen (auto-advance after 2s)
  • Simulated loading state (skeleton → content)
  • Auto-advancing onboarding slides
  • Toast notification auto-dismiss

Setting the delay

In the interaction panel, set After Delay and enter milliseconds (e.g. 2000 = 2 seconds). Chain multiple delays to simulate a loading sequence.

⌨️ Key / Gamepad

When to use it

Desktop app prototypes where keyboard shortcuts are core to the UX (Ctrl+S = save, Escape = close modal). Also useful for testing kiosk interfaces or screen-reader navigation patterns.

How to set it

Select trigger → Key/Gamepad → click the key field and press the actual keyboard key you want to bind. Works in Figma's Preview player, not in embedded share links.

📖 Glossary of Terms

Glossary

  • UI (User Interface): The visual part of an application that the user interacts with.
  • Component: A reusable, self-contained piece of the UI, like a button or a search bar.
  • State: The visual appearance of a component based on user interaction (e.g., hover, disabled).

A.1 Element: Buttons

Clickable elements that allow a user to trigger an action, like submitting a form, confirming a choice, or navigating.

  • The most important action on a page should be the most prominent button (Primary).
  • Button labels should be clear, action-oriented verbs (e.g., "Save", "Submit", "Cancel").
  • Ensure buttons have clear 'hover' and 'disabled' states.

A.2 Element: Input Fields

Form elements that allow users to enter information, such as text, numbers, or selections.

  • Always use a clear label for each input field.
  • Use placeholder text as a hint, not as a label.
  • Use the correct input type for the required data (e.g., 'password' type to mask text).

A.3 Element: Navigation

A collection of links and components that help users move between different sections of an application.

A.4 Element: Cards

Rectangular containers that group related information into a digestible chunk. They are a common way to display a collection of items.

A.5 Element: Modals (Pop-ups)

A dialog box or pop-up window that appears on top of the main page content, requiring the user to interact with it before they can return to the page.

  • Use them sparingly, as they interrupt the user's flow.
  • They are best used for critical actions, confirmations, or short forms.
  • Always provide a clear way to close the modal (an 'X' button or a 'Cancel' button).

A.6 Grid & Sizing Conventions

Grid & Layout:

  • 8-Point Grid System: All sizes, margins, and padding should be in multiples of 8 (e.g., 8, 16, 24, 32pt).
  • Columns: Mobile designs typically use a 4-column grid.
  • Margins: Space on the left/right edges. Standard is 16pt.
  • Gutters: Space *between* columns. Standard is 16pt.

Sizing & Spacing (Tap Targets):

  • Minimum Tap Target: Any interactive element must have a minimum tappable area of 44 x 44pt.
  • Buttons (Height): 44pt, 48pt, or 56pt.
  • Icons (Visual Size): 24 x 24pt (but ensure the tappable area is at least 44x44pt).
